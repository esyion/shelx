## 设计要点

### A. workflow 结构（3 个 job）

| job | runner | 职责 |
|---|---|---|
| `create-release` | ubuntu-latest | 校验 tag 与 `tauri.conf.json` version 一致 → 创建 draft release |
| `publish-tauri` | matrix 4 个 runner | 调用 `tauri-action@v1` build + 上传产物到 draft release + 自动产出 latest.json |
| `publish-release` | ubuntu-latest | 重写 latest.json 里的 URL 为公开 downloads 链接 → 把 release 从 draft 改为 published |

### B. matrix（4 个 target）

| label | runner | extra args |
|---|---|---|
| macOS Apple Silicon | `macos-latest` | `--target aarch64-apple-darwin` |
| macOS Intel | `macos-latest` | `--target x86_64-apple-darwin` |
| Linux x64 | `ubuntu-22.04` | (无) |
| Windows x64 | `windows-latest` | (无) |

不引 `windows-latest` 的 `ubuntu-22.04`：transpop 用 `ubuntu-22.04`（更稳定 LTS 镜像，macOS/Windows 用默认）。保持一致。

### C. 跟 transpop 的**差异**（有意保留，不照搬）

1. **触发方式**：shelx 只保留 `push: tags: ['v*']`，**不**加 `workflow_dispatch`。少一个 `RELEASE_TAG` env 和 verify tag 的 pwsh step。
2. **bundles**：当前 release.yml 在 4 个 OS step 里写死 `--bundles appimage,deb` / `msi` / `app,dmg`。tauri-action 不传 `--bundles` 时按 `tauri.conf.json.bundle.targets: "all"` 走 —— 配置里已经是 `"all"`，所以 4 个 job 都不传 `--bundles`，依赖 `tauri.conf.json` 单一来源；这样如果以后加新平台/格式只改 conf.json。
4. **Linux 双产物**：transpop 在 matrix 入口只跑一次 ubuntu，bundle 走默认全打。shelx 现状出 AppImage + deb（这两个都在 `"all"` 里），**自然被覆盖** —— 不需要 special-casing。但要确认 `tauri.conf.json.bundle.targets: "all"` 在 Linux 平台确实产出这两个（这是 Tauri 默认行为，应该没问题；如有问题在 run 时回头补 `targets: ["appimage", "deb"]`）。
5. **macOS 签名**：transpop 用 `APPLE_SIGNING_IDENTITY: '-'` 当占位（让 tauri-action 不签名但走完流程）。shelx 当前没 Apple 证书，**也加这一行保持占位**，避免 ci 跑崩；等未来接入 Developer ID 再换真证书。这跟现状行为一致，CI 产物依然未签名。
6. **Linux 系统依赖**：transpop 的 apt-get 列表跟现状 release.yml 第 42-49 行基本一致，但多了 `libfuse2`、`xdg-utils`、`libxdo-dev`、`wget`、`curl`。直接抄 transpop 的完整列表，避免漏。

### E. 命名约定（保留现状文件名，README 不破）

`releaseAssetNamePattern: shelx_[version]_[platform]_[arch][setup].[ext]`

但 tauri-action 不支持平台条件分支命名前缀。最接近现状的方案 —— 改用 `releaseAssetNamePattern: ${{ matrix.assetPattern }}` 配合 matrix：

```yaml
matrix:
  include:
    - label: macOS Apple Silicon
      assetPattern: shelx_[version]_macOS_aarch64[setup].[ext]
    - label: macOS Intel
      assetPattern: shelx_[version]_macOS_x64[setup].[ext]
    - label: Linux x64
      assetPattern: shelx_[version]_Linux_x86_64[setup].[ext]
    - label: Windows x64
      assetPattern: shelx_[version]_Windows_x86_64[setup].[ext]
```

文件名含义跟 README 第 13-22 行表格 1:1 对应（README 写 `shelx-<version>-Windows.msi`，这里出 `shelx_0.2.4_Windows_x86_64.msi` —— 字面有差异，需要在 CHANGELOG 条目里同步说明）。

**或者**保守一点：去掉 `releaseAssetNamePattern`，让 tauri-action 用默认名（`shelx_0.2.4_aarch64.app` / `shelx_0.2.4_x64-setup.exe` 等），README 章节也需要一并更新。**倾向后者**：跟 transpop 完全对齐，README 同步改一份下载表格，更透明。

## 风险与回滚

- **风险 1：tauri-action 默认产物名跟 README 写的下载表对不上** → 不影响功能（用户能下载到正确文件），仅是文件名不同。README 同步是单独 PR。
- **风险 2：第一次跑 secrets 里的私钥可能真的有问题（之前看到的报错）** → tauri-action 仍然吃 `TAURI_SIGNING_PRIVATE_KEY` env，行为跟之前一样；不增加新的失败面。这次能确认私钥格式/密码对错就当是顺带修了。
- **风险 3：撤销** → 把 release.yml 整个 checkout 回 main 上的 commit 即可。CHANGELOG 改动独立，可单独 revert。
- **回滚操作**：`git revert <merge-commit> && git push origin main`，无需 force push（仓库目前还是只用 tag 触发，main 上没产物副作用）。
